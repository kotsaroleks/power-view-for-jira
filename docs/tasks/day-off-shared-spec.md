# ТЗ: Day Off — прямий запис у GitHub без сервера

Дата: 2026-11-02. Статус: GitHub runtime реалізовано локально; реальне сховище
налаштоване, API читання/запис перевірено; командна перевірка ще не завершена. Цей
документ замінює попередні схеми Day Off через персональний Google OAuth, ручні Google ↔
Jira прив'язки, Google Sheet та окремий сервер.

## 1. Погоджений результат

Власник застосунку один раз задає спільний GitHub-токен і окремий репозиторій даних. Токен
входить до розширення. Усі встановлення PowerView використовують цей доступ для прямого
читання/запису JSON-файлів через GitHub API. Сервера немає.

Учасник уже працює в Jira: відкриває PowerView, ставить Day Off під датою табеля.
Застосунок сам визначає поточного Jira-користувача й записує його день у потрібний файл.
Інші учасники читають той самий стан у Time Report.

Учасникам не потрібні Google/GitHub-вхід, персональні токени, доступ їхніх GitHub акаунтів
до репозиторію, ручне зіставлення email або створення календаря.

## 2. Особа й доступ — конкретні джерела

- Jira-особа: поточна Jira-сесія, `GET /rest/api/3/myself` через наявний
  `CloudTimesheetClient.getUser()` / `RuntimeJiraTransport`.
- Доступ до файлів: спільний GitHub-токен у розширенні. Це обліковий доступ застосунку до
  репозиторію, а не скопійована браузерна Google/Jira-сесія.
- Ключ власника Day Off: Jira instance + accountId. Імена та email — допоміжні поля, їхня
  зміна не переносить історію. Google-адреса не потрібна.
- Поточний користувач визначає власника зміни. Вибір іншої людини у Time Report не
  перемикає власника запису.
- Перед зміною перевіряти поточну Jira-особу. При зміні сесії скасувати незавершені дії
  попереднього користувача; не застосовувати пізні відповіді до нового стану.

Google runtime, OAuth-конфігурацію та старі Google-тести видалено за прямою вказівкою
користувача. Цільовий runtime використовує `browser-github-day-off.ts` /
`GitHubDayOffStore.ts`; спільні контракти — `DayOffStore.ts`.

## 3. Одноразове налаштування власником

- Окремий приватний репозиторій тільки для даних PowerView. Репозиторій вихідного коду
  застосунку не використовувати як сховище Day Off.
- Fine-grained GitHub personal access token: доступ лише до вибраного репозиторію,
  `Contents: read and write`, без адміністративних прав та доступу до інших репозиторіїв.
- Фіксовані owner, repo, branch і кореневий каталог даних задаються разом із токеном один
  раз у конфігурації збірки. Не питати ці параметри у кожного учасника.
- Вихідний конфіг із реальним токеном не комітити. Для збірки передавати його через
  локальний ігнорований файл або змінну оточення; у вихідному коді тримати лише шаблон. У
  встановлюваній збірці токен присутній за погодженою схемою.
- При відсутній конфігурації показати «Сховище Day Off не налаштоване», а не Connect
  Google або запит входу учасника в GitHub.
- Відкликання/закінчення токена відображати як недоступний доступ застосунку. Заміна
  токена власником вимагає доставки оновленої конфігурації/збірки встановленням.

### Фактичні межі спільного токена

Токен у розширенні можна витягнути. Кожен власник копії розширення потенційно може читати
й змінювати вміст дозволеного репозиторію через GitHub API поза PowerView. Fine-grained
Contents permissions обмежуються репозиторієм, а не окремим JSON-файлом. Приватність
репозиторію не приховує його дані від власника цього токена.

Звичайний UI змінює тільки власні дні, визначені Jira `/myself`. Це клієнтське правило, а
не серверна ізоляція між учасниками: спільний токен не дає GitHub змоги перевіряти
Jira-особу. GitHub-автор коміту також не є доказом особи Jira-користувача. Не заявляти
неможливість підміни чужого accountId або захищений аудит авторства.

Ці межі документуються як властивість обраної простої схеми. Не додавати сервер,
персональну авторизацію або встановлення Jira-застосунку як приховану передумову.

## 4. Файли й прямий GitHub API

Використовувати GitHub Contents API: читання й створення/оновлення файлу. GitHub Pages,
Actions, Issues і pull requests для збереження Day Off не потрібні.

Схема файлів:

- `teams/<instance-key>/<team-id>.json` — останній успішно синхронізований склад
  Jira-команди.
- `day-off/<instance-key>/<account-key>/<YYYY-MM>.json` — дні однієї людини за місяць.

`instance-key` і `account-key` — детерміноване безпечне кодування нормалізованого Jira
instance та accountId. Не використовувати displayName/email у шляхах; не дозволяти
довільні шляхи, `..` або запис поза фіксованим коренем. У вмісті зберігати вихідні ID.
Окремі файли людей/місяців зменшують конфлікти паралельних записів.

Місячний запис: `schemaVersion`, `jiraBaseUrl`, `jiraAccountId`, `month`, набір дат Day
Off, `updatedAt`. За потреби ім'я зберігається лише для відображення. Зберігати лише
потрібні для функції дані, без Jira cookies, Google-токенів або вмісту worklogs.

Послідовність зміни:

1. Перевірити актуального Jira-користувача та календарну дату.
2. Прочитати відповідний JSON-файл і поточний GitHub SHA. Новий файл створювати
   автоматично; попередня ручна реєстрація людини не потрібна.
3. Змінити лише вибрану дату: додати до набору Day Off або прибрати з нього.
4. Оновити файл через GitHub API з поточним SHA; для нового файлу — створення без SHA.
5. Після підтвердження API показати збережений стан і оновити активний звіт.

При конфлікті SHA перечитати файл і зберегти сторонні зміни. Якщо потрібна дата вже має
бажаний стан — не створювати зайвий коміт. Якщо та сама дата змінилася відносно
прочитаного стану — показати конфлікт, не перезаписувати мовчки. Повтори обмежені.

При втраті відповіді після запису перечитати стан, не відправляти запис сліпо повторно.
Помилки доступу, мережі, невалідний JSON, конфлікт і rate limit показувати окремо.
Недоступність репозиторію/гілки не видавати за відсутній календар. Відсутній місячний файл
означає відсутність позначок лише після підтвердження доступу до правильного репозиторію й
гілки; неоднозначний 404 не є порожнім успішним читанням.

Токен передавати тільки до GitHub API у заголовку авторизації. Не включати його у URL,
коміти, текст помилок, діагностику або скриншоти. Запитувати потрібний Chrome host
permission GitHub один раз; Jira Grant access не замінює доступ до GitHub API.

## 5. UX Timesheet

- Day Off — прапорець під датою заголовка тижневої таблиці. Дата й власник уже відомі; без
  popup, вибору задачі/акаунта та зайвих полів.
- Немає Connect Google / Disconnect Google / GitHub login для учасників.
- Видимі стани: завантаження, збереження, збережено, помилка. Заблокований прапорець
  повинен мати конкретне пояснення, а не залишатися незрозуміло неклікабельним.
- Помилка не створює видимість успішного командного збереження. localStorage/IndexedDB
  допустимі лише як кеш із позначенням актуальності, не як прихована заміна GitHub.
- Наявні worklogs не видаляти/змінювати. При відомому власному часі на дату блокувати нову
  позначку з поясненням; існуючий конфлікт показувати.
- При Day Off блокувати нове логування через PowerView. Скасування позначки не створює
  worklog. Неповні дані не доводять відсутність конфлікту.
- Порядок задач зберегти: pin → власні worklogs тижня → LBR-68393 і нащадки → решта
  призначених мені задач борди → інші задачі борди.

## 6. Команда та Time Report

- Команди/учасники — з Jira через `CloudTeamsClient`, із повною пагінацією. Склад можна
  синхронізувати у GitHub; джерелом складу лишається Jira.
- Людина з'являється у списку за членством Jira-команди, без Google/GitHub-входу та
  незалежно від наявності worklogs чи першої позначки Day Off.
- Оновлення складу не видаляє історію колишніх учасників і не змінює членство в Jira.
- Time Report читає ті самі місячні JSON-файли потрібних людей/дат. Доступ здійснює
  застосунок через спільний токен незалежно від Google/GitHub-акаунта переглядача.
- Робочий Day Off зменшує чинну денну норму на 8 годин один раз. Позначка вихідного не
  віднімає додаткові 8 годин від нульової норми. Показувати конфлікти з годинами.
- Capacity/utilization обчислювати лише за повними даними. Збій читання — «дані
  недоступні», а не нуль Day Off.
- Інші встановлення бачать зміни після повторного читання/Refresh. Realtime не є вимогою.
  Кешувати незмінені файли й обмежувати запити до GitHub.

## 7. Наявні дані й обмеження

- Google Sheet та його дані не видаляти. Локальний Google-код і OAuth-конфігурацію
  видалено за наступною прямою вказівкою користувача. Перенесення наявних позначок —
  окрема контрольована операція зі збереженням Jira ID та дат, перевіркою результату й без
  автоматичного видалення джерела.
- Не створювати сервер, Forge/Connect, службові Jira-задачі, коментарі чи фіктивні
  worklogs. Встановлення застосунку в Stryker Jira заборонене.
- Повторно використовувати чинний Chrome-дозвіл Jira. При втраті content script
  відновлювати зв'язок; не показувати повторний Grant access, якщо дозвіл уже надано.
- Цей документ не містить реального токена, не створює репозиторій і не підтверджує його
  налаштування. Поточне призначення: `kotsaroleks/power-view-jira-data`, `main`,
  `powerview`; налаштування й API перевірку зафіксовано в окремому setup-документі.

## 8. Приймання

1. Два встановлення з різними Jira-користувачами, без Google/GitHub-підключення учасників,
   зберігають власні Day Off через один налаштований доступ застосунку.
2. Перший користувач бачить дні другого у Time Report після Refresh; зміни зберігаються
   після закриття/повторного відкриття. Локальний кеш не маскує збій запису.
3. Новій людині не потрібні ручна Google-прив'язка, персональний токен або календар.
4. Зміни різних дат з двох клієнтів одного користувача не губляться при конфлікті SHA.
   Перевірити також одночасне створення відсутнього файлу й невідому відповідь запису.
5. Відкликаний/прострочений токен, відсутня гілка/репозиторій, rate limit, мережевий збій,
   невалідний файл і конфлікт дат мають відмінні стани помилок.
6. UI визначає власника через актуальне `/myself`. Зміна Jira-сесії або instance не змішує
   записи. Прямий доступ зі спільним токеном має описані вище широкі права; тест не
   видається за серверну ізоляцію Jira-користувачів.
7. Чинні Chrome-дозволи не запитуються повторно. Дані пишуться лише у налаштований
   репозиторій/гілку/корінь; токен не потрапляє у логи/діагностику/вихідний Git.
8. Окремо перевірені прапорці, скасування, робоча норма, конфлікт із worklogs та
   збереження існуючого UX задач.

Fixtures і модульні тести не замінюють фактичний тест двох встановлень. До виконання
критеріїв статус — «GitHub-збереження та командна перевірка не завершені».

Локальне налаштування та поточні межі перевірки: [GitHub setup](day-off-github-setup.md).
