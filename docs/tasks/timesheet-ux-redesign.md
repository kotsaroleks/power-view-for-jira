# Задача: новий UX тижневого логування часу без дропдаунів задач

Дата: 2026-11-02. Проєкт: Power View for Jira, Chrome extension. Статус: ТЗ для передачі в
новий локальний чат; погоджений UX реалізовано локально 2026-11-02. Перевірки й межі
валідації описані в `timesheet-ux-local-handoff.md`.

## Актуалізація: Day Off та Jira-особа

[Актуальне ТЗ Day Off](day-off-shared-spec.md): поточна Jira-сесія визначає особу; один
спільний GitHub-токен у розширенні дає прямий запис у JSON окремого репозиторію. Без
сервера, персонального Google/GitHub-входу та ручних прив'язок учасників. GitHub runtime
та сховище налаштовані; готовність UX табеля не замінює перевірку Day Off двома
встановленнями.

## Уточнення користувача 2026-11-02: деталі worklog

Кнопка «…» біля годин має пояснювальну підказку на hover/фокусі. Деталі запису,
редагування, видалення й додавання окремого worklog із деталей відкриваються у спливному
вікні поверх таблиці. Esc/закриття повертає фокус у відповідну комірку; незбережені зміни
й невідомі результати запису зберігають чинні guards. Це нова пряма вказівка, яка замінює
попередню вимогу inline-блоку саме для деталей. Основне введення годин і вибір задач
залишаються в таблиці, без dropdown задач.

## 1. Причина та очікуваний результат

Користувач категорично відхилив поточний UX. Його пряма вимога:

> Те що є зараз — категорично не підходить. Обирати таски з дропдауна — це брєд.

Потрібно спроєктувати новий UX тижневого табеля, де людина бачить задачі в погодженому
порядку груп, може закріпити потрібні та вводить години безпосередньо в таблицю. Поточний
інтерфейс не є погодженим макетом. Успішні тести та готова збірка попередньої версії не
означають прийняття її UX користувачем.

Цей документ замінює попередні вимоги щодо дропдаунів вибору Epic/Story/Task/Subtask.
Правила авторства worklog, Jira API та цілісності даних залишаються чинними.

## 2. Підтверджені рішення користувача

1. Обрати й запам'ятати борду. Задачі борди — усі доступні задачі її збереженого фільтра,
   включно із задачами, яких не видно в колонках борди.
2. «Призначені мені» — задачі саме обраної борди, де Assignee.accountId дорівнює accountId
   поточного користувача. Reporter, автор worklog і displayName не замінюють Assignee.
3. Враховуються Epic, Story, Task і Subtask. Статусний фільтр користувач не задавав.
4. Задачі видно до логування часу; нуль залогованих годин не ховає їх.
5. Закріплення задач зберігається між тижнями. Користувач погодив можливість закріплення
   будь-якого з перелічених рівнів, а не лише Epic/Story.
6. Порядок груп: закріплені незалежно від Assignee → задачі з власним worklog за обраний
   тиждень (також поза бордою) → пріоритетний Epic LBR-68393 та його нащадки → решта задач
   борди, призначених користувачу → усі інші задачі борди. Кожна задача показується один
   раз у першій відповідній групі.
7. Для Epic потрібен спільний перелік підзадач із групуванням за Story, без обов'язкового
   послідовного вибору Epic → Story → Subtask. Форма цього переліку тепер має бути видимою
   після розгортання, без дропдауна. У групі «Інші задачі» ієрархія Epic → Story →
   Task/Subtask початково згорнута. Задачі без Epic/Story показуються окремою групою «Без
   батьківської задачі».
8. Основний екран — тижневий табель навіть після раніше збереженого режиму Month.
   Загальної кнопки Log time і модального вибору задач немає. Години вводяться в тижневій
   таблиці, без повторного вибору задачі й дати та без обов'язкового заповнення опису або
   часу початку.
9. Новий worklog з комірки починається о **09:00 дати колонки в обраному часовому поясі**.
10. Якщо в комірці кілька worklog, їх редагують окремо через деталі. Автоматичне
    переписування агрегованої суми не погоджене.

## 3. Сценарії нового UX

### Відкриття табеля

- На першому відкритті обрати борду. Надалі використовувати запам'ятований вибір.
- Власні задачі вже показані як видимі рядки/список, без відкриття меню вибору задач.
- Якщо борда ще не обрана, показати зрозумілий початковий стан.
- Порядок груп зверху вниз:
  1. Закріплені задачі незалежно від Assignee.
  2. Решта задач із власним worklog за обраний тиждень, включно із задачами поза бордою.
  3. Пріоритетний Epic LBR-68393 (ARIA — Regular Project related activities) і його
     нащадки.
  4. Решта задач збереженого фільтра борди, призначених поточному користувачу.
  5. Усі інші задачі збереженого фільтра борди у початково згорнутій ієрархії.
- Задачі з власним часом за обраний тиждень залишаються доступними після зміни борди або
  Assignee. Автор worklog, а не поточний Assignee, визначає належність до другої групи.
- Кожну задачу показувати один раз у першій відповідній групі. Зокрема, закріплена задача
  з власним часом залишається лише в першій групі; її години враховуються один раз.

### Закріплення

- Дія «закріпити/відкріпити» безпосередньо біля задачі, з видимим станом.
- Закріплення не вимагає створювати порожній/фіктивний worklog.
- Зняття закріплення не видаляє час і не ховає наявні записи тижня.
- Ізоляція налаштувань: Jira instance, користувач, борда.
- Недоступна закріплена задача не зникає без пояснення; дати змогу прибрати закріплення.

### Вибір інших задач

- «Інші задачі» — п’ята група табеля, яка охоплює решту всіх задач збереженого фільтра
  борди. Після розгортання задачі показуються звичайними видимими рядками.
- Пошук за ключем і назвою фільтрує цей список без переходу до форми логування.
- Додавання задачі до табеля — явна дія на її рядку; це не створення worklog.
- Epic/Story початково згорнуті та розгортаються у видиму ієрархію Epic → Story →
  Task/Subtask. Для Epic підзадачі згруповані за їхньою Story.
- Задачі без Epic/Story показуються окремою групою «Без батьківської задачі».
- Ієрархія не створює повторних рядків задач, уже показаних у попередніх групах.
- Заборонені native select, searchable select, combobox та їхні стилізовані аналоги для
  вибору задач, Epic або Story. Пошуковий список/дерево не маскувати під dropdown.
- Ця заборона стосується вибору задач; спосіб вибору борди користувач окремо не забороняв.

### Введення часу

- Рядки — конкретні Jira-задачі, колонки — дні тижня, комірки — тривалість.
- Клік у комірку → введення → Tab/Enter/втрата фокуса → збереження.
- Підтримати `2`, `1.5`, `1,5`, `1:30`; пояснення формату компактне, не повторюється в
  кожній комірці.
- Порожня комірка доступна для введення; для одного worklog редагується його тривалість.
- Для кількох worklog комірка показує суму та відкриває деталі окремих записів.
- Опис, точний час початку та видалення — додаткові дії, не обов'язкові кроки основного
  сценарію. За новим уточненням користувача деталі й форма конкретного запису
  відкриваються у спливному вікні поверх таблиці, без повторного вибору задачі.
- Показувати стани збереження та помилки. При помилці введене значення не губиться.
- Не показувати чернетку як уже збережені в Jira години.
- Видимі підсумки за рядком, днем і тижнем; сьогоднішній день виділений.
- Таблиця має залишатися головною частиною екрана, без великих технічних блоків над нею.
- Перенесення задач минулого тижня переносить лише рядки, без годин.

## 4. Вимоги до даних і безпеки записів

- Assignee визначає список власних задач. Автор worklog визначає, чий час відображається і
  редагується. Це різні поняття, їх не можна змішувати.
- Борда є контекстом вибору задач; не застосовувати її непомітно як фільтр усієї особистої
  історії часу. Не втрачати записи через зміну борди або Assignee.
- Поточний адаптер бере saved filter ID із конфігурації борди та шукає задачі за ним,
  оскільки board issue endpoint не повертає Scrum Epic. Збережений фільтр є погодженою
  межею задач борди для цього UX; видимість задачі в колонках не є додатковою умовою.
- Не робити запити worklog для всіх задач борди тільки заради списку вибору.
- При зміні одного запису зберігати його точний timestamp та повний коментар.
- До запису перевіряти поточного Jira-користувача і актуальність даних комірки.
- За конфлікту не перезаписувати чужі/паралельні зміни; запропонувати перечитування.
- За невідомого результату POST не повторювати створення автоматично.
- Підтверджений запис із невдалим наступним читанням не відправляти вдруге.
- Нуль/очищення комірки не повинні непомітно видаляти Jira-worklog.
- Повна пагінація; явні стани завантаження, порожнього списку, недоступності та часткової
  помилки.
- Скасування запитів і захист від запізнілих відповідей при зміні контексту.
- Дані та закріплення одного акаунта/instance не показувати іншому.

## 5. Критерії приймання

- AC-01: після відкриття запам'ятованої борди користувач бачить власні задачі без
  відкриття жодного селектора задач, зокрема задачі без worklog.
- AC-02: для введення годин у видиму задачу не потрібні пошук, dropdown або модальний Log
  time. Загальних кнопок Log time немає; вибір задач і основне введення відбуваються на
  основному екрані. Додаткове редагування конкретного worklog — спливне вікно за новим
  уточненням користувача. Початковий режим завжди Week, навіть зі збереженим Month.
- AC-03: закріплення доступне на рядку задачі та відновлюється після переходу на інший
  тиждень і повторного відкриття табеля.
- AC-04: «Інші задачі» містить видимі результати пошуку та рядкові дії
  додавання/закріплення.
- AC-05: ієрархія Epic → Story → Task/Subtask у групі «Інші задачі» початково згорнута й
  розгортається без select/combobox. Задачі без Epic/Story доступні в окремій групі «Без
  батьківської задачі».
- AC-06: зміна часу в комірці з одним записом не змінює його опис або фактичний timestamp.
- AC-07: комірка з кількома записами відкриває індивідуальні worklog; агрегат автоматично
  не переписується.
- AC-08: Tab дає передбачуваний рух між комірками; збереження сусідньої комірки не знищує
  текст, який користувач уже вводить у наступній.
- AC-09: помилка мережі/конфлікт/невідомий результат не спричиняють втрати введеного або
  дублювання часу.
- AC-10: при 1440×900 і 1280×800 видно таблицю та щонайменше п'ять рядків, якщо вони є;
  перевірити масштаб 200%, клавіатуру, довгі назви та великі списки задач.
- AC-11: реальні скріншоти production-збірки показують початковий стан, власні задачі,
  закріплені рядки, «Інші задачі», ієрархію Epic і введення часу. Якщо браузер не
  запустився, не видавати тести/макет за візуальну перевірку.

- AC-12: порядок груп — pin незалежно від Assignee → власний час за обраний тиждень →
  пріоритетний Epic LBR-68393 та його нащадки → решта призначених користувачу задач борди
  → всі інші задачі борди. Перевірити чужу закріплену задачу та задачу, яка одночасно
  відповідає першим трьом групам: один рядок, один облік її часу.
- AC-13: задача збереженого фільтра, не видима в колонках борди, залишається доступною.
  Задача поза цим фільтром із власним часом за обраний тиждень залишається в другій групі
  після перемикання борди, якщо не належить до першої групи.

- AC-14: LBR-68393 має пріоритет у табелі лише для stryker-emergencycare.atlassian.net.
  Pin і власний час завжди вищі; нащадки Epic успадковують пріоритет, без дублів. Поле
  Priority в Jira не змінюється. Налаштування ізольоване за instance/account; явно
  збережений порожній список скасовує початковий пріоритет.

## 6. Межі задачі та передача результату

Результат задачі — новий UX тижневого табеля з конкретним макетом/прототипом, описом
взаємодій і критеріїв перевірки. При реалізації орієнтуватися на ці сценарії, а не на
косметичне перефарбування існуючих дропдаунів. Нові бізнес-правила, яких немає в цьому
документі, не вигадувати; суттєві питання уточнювати.

Approval і billing не входять до цієї задачі. Day Off та його відображення у командному
Time Report додатково замовлені користувачем і мають окреме актуальне ТЗ
`day-off-shared-spec.md`; старе виключення Day Off зі scope більше не застосовується.

Для локального продовження, наявного коду, перевірок і відомих обмежень див.
`timesheet-ux-local-handoff.md` у цій самій директорії.
