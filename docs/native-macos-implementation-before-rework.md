# Нативний Power View — стан реалізації

Дата: 2026-10-16. Джерело: повністю прочитане `native-macos-product-spec.md`. Етап 1
триває; наскрізний пілот на реальному релізі ще не пройдено. Попередні
Safari/Electron-зміни й продуктове ТЗ збережені без перезаписування.

## Запуск

```sh
sh scripts/build-native-macos.sh
```

Результат: `apps/macos/dist/Power View.app`. Це нативний SwiftUI/AppKit-застосунок, без
web-wrapper. Пакет містить реєстрацію `.pvrelease` і локальний ad-hoc підпис; нотаризація,
дистрибуція та оновлення ще не виконані. Для розробки можна відкрити
`apps/macos/Package.swift` у Xcode. Поточне припущення — macOS 14+, перевірено на Apple
Silicon.

У новому вікні створити локальний реліз одного Jira-проєкту, задати координатора,
учасників і ролі. У локальному режимі перемикач учасника служить для перевірки сценаріїв;
це не автентифікація. Після Jira-підключення перемикач вимикається, особа береться з
`myself`, мережевий запис дозволяється лише для цієї особи. Кожен користувач підключає
власний email/API token у вікні Jira. Токен зберігається в Keychain, не в документі.
Поточний адаптер підтримує Jira Cloud REST v3; Data Center ще не реалізовано.

## Реалізовані частини

- На старті доступний заповнений приклад із вигаданими сторіз DEMO-1/DEMO-2, готовими
  матеріалами ТЛ/QA та експортом Excel: 3,6 + 6 = 9,6 люд.-дн. Приклад прив’язаний до
  зарезервованого `.invalid` origin і не працює з реальною Jira. Перевірено відкриття й
  експорт через UI; файли прикладу лежать у `apps/macos/dist/Example`.
- Матеріали для ролей без права редагування показуються читабельним текстом, а не сірими
  вимкненими полями. Очікування Keychain при відкритті приватної чернетки перенесено з
  головного потоку; приклад не звертається до Keychain. Поки перевіряється відновлення,
  редагування блокується. Поточний набір: 49 Swift-тестів пройдено.
- FileDocument: створення, відкриття, збереження локального релізу, команда, ролі,
  додавання/вилучення сторіз, історичні скоупи та оцінки.
- XLSX: вибір аркуша/колонки, діагностика рядків, дублікати й чужий проєкт; завантаження
  доступних Jira-сторіз, явні помилки недоступних ключів; офлайн імпорт зберігає лише
  ключі й позначає необхідність Jira-завантаження.
- Імпортований реліз прив'язується до Jira-origin; інша інстанція відхиляється.
- Підготовка ТЛ → QA, повернення із зауваженнями, повторні підтвердження та окрема дія
  готовності. Не потрібне призначення виконавців. Немає автоматичної зміни Jira-статусу.
- dev = сума dev-підзадач; QA = 20% або явна оцінка; сторі = dev + QA; день = 8 годин.
  Буфер 15%, редагується ТЛ/координатором і не входить у Jira/клієнтські оцінки.
- QA-підзадача зіставляється явно за ключем, а не за словом у назві. Plan/fact dev та QA
  читає worklog підзадач і виключає батьківську сторі; недоступні дані показуються як N/A.
- Читання сторіз, усіх сторінок коментарів і підзадач; автоматичне оновлення коментарів
  всіх сторіз релізу раз на 60 секунд. Нові й змінені коментарі позначаються у списку;
  прочитання зберігається між запусками окремо для користувача та Jira.
- Незмінний preview точного JSON: коментар, реальна підзадача, Original Estimate,
  додавання AC/DoD в опис і додавання лише наявної Fix Version після погодження замовника.
- Перед записом: перевірка особи, origin, точних маршрутів і `updated` задач. Застарілий
  preview відхиляється. Операції не повторюються автоматично. Пакет Fix Version показує
  succeeded/failed/uncertain/notAttempted окремо по цілях.
- Журнал наміру запису зберігається до мутації. Збій журналу блокує запис; незавершений
  журнал після crash вимагає звірки Jira.
- Клієнтський XLSX містить лише ключ і загальну оцінку, без буфера й декомпозиції; експорт
  блокується до готовності всіх сторіз. Зміни скоупу скидають клієнтське погодження.
- Приватні AES-GCM-чернетки, ключ автора в Keychain, збереження кожної зміни полів, diff і
  вибіркове відновлення. Відкладене відновлення блокує подальше редагування, щоб нова
  робота не затирала чернетку. Підтвердження й стан workflow автоматично не відновлюються.
- Нативний ручний Reporting, immutable локальна історія, EN/UK stand-up, PDF, обробка
  скасування та неповних даних. Live генератор завантажує також задачі борду для історії
  вилучених сторіз і враховує worklog авторів поза current assignee.

## Контрольні перевірки

```sh
CLANG_MODULE_CACHE_PATH=/tmp/power-view-clang-cache \
SWIFTPM_MODULECACHE_OVERRIDE=/tmp/power-view-module-cache \
swift test --disable-sandbox --package-path apps/macos --scratch-path /tmp/power-view-swift-build
node --test prototypes/drive-lease/LeaseService.test.mjs
node --experimental-strip-types scripts/native-report-fixtures.mjs
```

Поточний результат: 43 Swift-тести пройдено, включно з повним синтетичним шляхом Excel →
ТЛ → повернення QA → готовність → експорт → погодження. Це не живий пілот.

Кеші перенаправлено в `/tmp` через обмеження середовища. SwiftUI executable компілюється
разом із тестами. Контрольні JSON fixtures створює попереднє TypeScript-ядро, Swift їх
лише читає. Зміни старої реалізації для підгонки результатів не виконувалися.

Вручну в зібраному `.app` перевірені створення релізу, додавання сторі та учасника,
збереження `.pvrelease`, рольові обмеження полів, ізоляція незбережених полів ТЛ від
координатора та відновлення тільки вибраного AC без перенесення DoD. Записаний файл
додатково перевірено читанням із диска. Живих Jira/Drive-даних не змінено.

| Board Health / Sprint Health                      | `domain/report.ts`                      | Pure Swift збігається з 2 golden-наборами; UI показує Board Health summary                            |

Окремий Board Health читає весь борд і перевіряє склад спринтів через Jira. Блокування
обчислюються за статусом і залежностями; окремий golden-тест звіряє їх зі старим продуктом
без перенесення планувальника. Недоступні дані показуються як N/A. Продуктивність і
паритет на великому реальному борді ще не підтверджені.

## Drive — невиконаний критерій приймання

Оновлення 2026-10-19: додано прямий Drive REST-клієнт створення `.pvrelease` у вибраній
папці й завантаження точних байтів назад. Створюється новий snapshot, без перезаписування
спільного файла. Перевірено multipart, фіксований Google-host, відхилення некоректних ID,
відсутність повтору запису після 403. У Google OAuth прибрано вимогу Apps Script
deployment, доступ обмежено `drive.file`. Додано дію збереження копії в інтерфейсі,
браузерний PKCE-вхід із loopback-відповіддю лише на 127.0.0.1, timeout і скасуванням,
Keychain-відновлення входу та вихід. За замовчуванням копія створюється в «Мій диск»;
посилання на іншу папку потребує попередньо наданого застосунку доступу. Повноцінний
picker папок ще не реалізовано. У збірці немає зареєстрованого Google OAuth client ID
Power View; без нього реальний вхід Google неможливий. Збирач приймає
`POWER_VIEW_GOOGLE_CLIENT_ID` і, для desktop client, `POWER_VIEW_GOOGLE_CLIENT_SECRET`;
вони потрапляють у bundle розробника. Це не користувацькі токени. Інтерфейс без
конфігурації пояснює недоступність входу. Таку реєстрацію виконує розробник продукту, не
кожен його користувач. 48 Swift-тестів пройдено; серед нових перевірок — state/host/port
callback, PKCE-обмін, кодування `+` у формі та відхилення непідтвердженої Google-особи. У
зібраному застосунку вручну перевірено нову дію Drive та повідомлення без конфігурації.
Реальний Google-вхід і завантаження на Drive ще не перевірені.

Додані серверний прототип і Swift-клієнт із lease, fencing, монотонним timeout, ревізіями
й квитанціями. Це не прапорець `locked=true`: фактичний серверний запис перебуває в
критичній секції. Але локальні тести з підставними Google-сервісами не доводять гарантію
на двох Mac.

[Протокол, налаштування й таблиця живих перевірок](../prototypes/drive-lease/README.md).
Повноцінний вибір папки, створення спільного файла та підключення lease до всіх дій UI ще
не завершені. UI явно позначає локальний режим і не обіцяє спільне редагування. Рішення з
додатковим Apps Script-сервісом призупинено після обговорення з користувачем. Воно не є
прийнятим способом інтеграції; налаштування Cloud-проєкту не є вимогою до користувача.
Збереження на Drive залишається незавершеним.

## Відомі обмеження перед пілотом

- Немає прийнятої живої перевірки A4–A6 та пілота від імпорту до Excel для ПМа.
- Google-вхід не налаштований у збірці, спільний файл не підключений; локальний файл не
  слід редагувати одночасно на двох Mac.
- Локальний перемикач учасників — тестовий режим; реальна роль для мережевого запису
  визначається лише verified account ID. Рольовий контроль UI не замінює ACL Drive/Jira.
- Чернетки шифруються, але ключі одного macOS-акаунта не захищають від власника цього
  OS-акаунта, який має повний доступ до Keychain. На спільному Mac потрібні окремі
  OS-акаунти.
- AC/DoD оновлює власну керовану секцію, зберігаючи сторонні ADF nodes; неоднозначні
  дублікати відхиляються до запису.
- Перевірка `updated` перед записом не є атомарною Jira-транзакцією; паралельні зовнішні
  записи в момент між читанням і PUT потребують окремої перевірки можливостей Jira.
- Додаткові обов'язкові custom fields при створенні підзадач поки не мають динамічного UI;
  така Jira-помилка показується, але не обходиться.
- Для Jira-запису підтримується точність до цілої хвилини. Дрібніші значення відхиляються
  до preview, без тихого округлення чи зміни формул; правило точнішого округлення ще не
  погоджене.
- Excel підтримує `.xlsx`, справжні назви аркушів і workbook relationships. `.xls`,
  клієнтський зразок, великі файли й форматування клієнтського експорту ще потребують
  перевірки.
- Історія зберігає сторіз і командні налаштування перед зміною; клієнтський архів містить
  точні байти XLSX, SHA-256 та автора. Погодження прив’язане до конкретного експорту.
  Зміна лише буфера зберігає погодження. Резервні копії на Drive ще не реалізовано.
- Gantt, ШІ, Google Sheets, календарі й хмарні розклади не реалізуються в цій частині.
