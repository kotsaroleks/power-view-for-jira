# Незалежний аудит ТЗ та виконання двох цілей Power View

Дата: 19 жовтня 2026 року. Виконавець: окремий агент-аудитор. Продуктний код не
змінювався.

## Вердикт

**Повний перенос Chrome-продукту у Swift не виконано. Функціональна дошка естимації у
native UI не реалізована як дошка.** Є справжній нативний застосунок, локальна модель
релізу, форма підготовки сторі, формули оцінок і частина інтеграційного коду. Це часткова
реалізація, а не еквівалент старого продукту плюс нова дошка.

**Саме ТЗ втратило частину початкової мети.** Воно описує новий процес підготовки релізу,
але не встановлює повний функціональний паритет із Chrome. Наявний Gantt не включено до
першого етапу; Status chart взагалі не має свого критерію; для естимації рекомендовано
«список сторіз → робоче місце сторі», а не визначено перевірювану дошку. Тому виконання
A1–A18 навіть теоретично не довело б виконання двох цілей користувача.

## Джерела та межі висновків

Головний критерій — пряме уточнення користувача: «Я просив переробити chrome app в свіфт
застосунок і додати в нього функціональну дошку с естимацією».

Повністю прочитано [наявне ТЗ](native-macos-product-spec.md), досліджено маршрути Chrome
UI, EstimationBoard і workflow, Gantt V2, Status chart, Reporting, налаштування та
Jira-клієнти; перевірено native SwiftUI entry point, форму, Jira/Drive/Reporting UI і
моделі. [Попередній exploratory-звіт](native-macos-independent-exploratory-audit.md)
використано як окреме джерело реально виконаних UI-перевірок. Цей аудит не видає їх за
нове незалежне відтворення: новий UI-сеанс і живі Jira/Drive-виклики тут не виконувалися.
Відсутність дошки/Gantt/Status підтверджена структурою підключеного Swift UI, а не лише
пошуком назв.

ТЗ саме називає себе документом, який ще не проходив фінального рев’ю
([рядок 6](native-macos-product-spec.md#L6)). Посилання на «продуктове інтерв’ю» не є
доступним транскриптом. Окремого первинного запису інтерв’ю в досліджених документах не
знайдено. **Не можна чесно стверджувати, що всі його деталі були вигадані, але не можна й
автоматично вважати їх схваленими користувачем.**

Історія підтверджує, що порівняння не засноване лише на незбережених нових файлах:
EstimationBoard включена у tracked commit `88f61ea` від 14.10.2026; Gantt V2 змінювався у
`3144274` від 13.10.2026; Status chart — `9e2f1a9` від 12.09.2026. Native ТЗ датоване
16.10.2026 і наразі untracked. Поточні web/extension-файли також мають попередні локальні
зміни: цей аудит не приписує кожній деталі точний момент замовлення і не змінює їх.

Позначення стану: **є локально** — підключено до UI та/або перевірено попереднім
exploratory; **частково** — частина шляху є, завершення не доведено; **немає** — немає
потрібного продуктового шляху; **не підтверджено** — код/тести не замінюють інтеграційне
приймання. Розрахунок у бібліотеці без екрана не зараховується як готова можливість.

## Що насправді переноситься з Chrome

Chrome-продукт — не лише Reporting. У [App.tsx:251](../apps/web/src/app/App.tsx#L251) є
окремі Workspace, Reports, Gantt, Status та Estimation, а маршрути реально підключають
компоненти ([App.tsx:531](../apps/web/src/app/App.tsx#L531),
[App.tsx:595](../apps/web/src/app/App.tsx#L595),
[App.tsx:621](../apps/web/src/app/App.tsx#L621)).

Доступні можливості:

- Налаштування Jira/workspace: проєкт, борд, JQL, mapping полів, completed-статуси,
  перенесення конфігурації без секретів; Cloud і Data Center у клієнтських адаптерах.
- Gantt: ієрархія задач, timeline/zoom, пошук і приховування завершених, сортування,
  локальні залежності, конфлікти, взаємодії зі смугами; дозволені Jira-редагування мають
  окремі шляхи й підтвердження. Поточний App підключає V2, тому старий legacy Gantt сам по
  собі не слід рахувати як другий окремий екран.
- Status chart: розподіл усіх завантажених задач за фактичними Jira-статусами з
  кількостями та відсотками.
- Reporting: Daily/Weekly/Sprint, Board Health, періоди/учасники/status mapping, history,
  stand-up і PDF. Повний паритет потребує перевірки інтерфейсу та результатів на однакових
  даних.
- Estimation вже має п’ять колонок, картки сторіз, пошук, кількість у релізі/ready та суму
  dev days; редагування TL/PM clarification/scope/QA, localStorage і JSON handoff. Це
  локальна підготовка, не створення subtasks або зміна status у Jira
  ([EstimationBoard.tsx:180](../apps/web/src/app/estimation/EstimationBoard.tsx#L180)).

Перенос у Swift не вимагає копіювати React, localStorage, браузерну вкладку чи механіку
extension. Але потребує збереження корисних користувацьких сценаріїв або явного погодження
їх вилучення. Заміна технології не є дозволом непомітно прибрати Gantt та Status.

## Estimation board: що фактично працює, а що відсутнє

**Підключено до native UI:** створення локального релізу; додавання/вилучення ключа; XLSX
preview/import; вибір сторі зі списку; AC/DoD, confirmations, QA-поля; показ dev/QA/client
estimates; локальні handoff/return/ready з gates; експорт для готового релізу. Попередній
exploratory реально перевірив частину цих локальних дій. Це не «нічого».

**Є у коді та UI, але не прийнято як живий процес:** Jira connection/import, створення й
оцінки реальних subtasks із preview, comments polling, запис parent estimate/AC/Fix
Version, plan/fact. Немає підтвердженого користувацького проходження на реальному релізі
різними ролями. Ready-стан у example або seeded файлі не є серверним доказом.

**Відсутнє у підключеному UI:** єдиний огляд колонок естимації, картки з оцінкою та
відповідальним, пошук/фільтри дошки, stage counters, повноцінна навігація між overview і
details без ризику втрати вводу. Усе native main view — NavigationSplitView/List/Form
([Swift:63](../apps/macos/Sources/PowerView/PowerViewApp.swift#L63),
[Swift:484](../apps/macos/Sources/PowerView/PowerViewApp.swift#L484)). Модель зі state
enum та кнопками переходів — важлива частина workflow, але не реалізована дошка.

**Drag-and-drop не вважається автоматично обов’язковим.** Chrome Estimation також
переводить картки за заповненням/підтвердженням, а не довільним drag. Достатні зрозумілі
дії з перевірками; неприпустимо вимагати придуману взаємодію лише через слово «дошка».
Конкретні колонки native можуть відповідати явно погодженому новому TL→QA процесу, а не
буквально п’яти старим назвам. Але одночасний огляд потоку і карток має існувати.

Дошка не повинна залежати від ручного підкладання fake evidence для показу сценарію. Якщо
її задумано як Jira-only, це має бути явне продуктове рішення з доступним шляхом
створити/змінити оцінку та видимою причиною відмови при недостатніх правах. Зараз
локальний чистий реліз не відтворює простий цикл ручної естимації старого Chrome без Jira.

Чесного числового відсотка немає: відсутній погоджений список можливостей із вагами й

Навіть «два модулі з чотирьох» не означає 50%: модулі неоднакового обсягу та стану
перевірки.

## Мінімально виправлений обсяг приймання

Це пропозиція заміни критеріїв саме двох цілей, а не нова самовільна архітектура. Вона не
скасовує окремі справді погоджені вимоги Drive/QA; їх треба прив’язати до джерел і додати
як окремий блок, а не використовувати замість переносу.

### Ціль 1 — Swift-версія існуючого продукту

1. Native app запускається на цільовому Mac, користувач підключає потрібну Jira, вибирає
   той самий проєкт/борд/JQL і отримує зрозумілі стани помилок/повноти.
2. Наявні Gantt, Status chart, Reporting доступні у native navigation. Кожен основний
   Chrome-сценарій має відповідник або окреме явне рішення про вилучення. Новий
   AI-планувальник, хмарні розклади й календарі не потрібні для переносу ручного Gantt.
3. На одному контрольному наборі Chrome і Swift порівнюються
   задачі/ієрархія/дати/залежності, status distribution, усі види звітів, фільтри та
   експорти. Перевіряються не лише pure calculations, а дії з UI.
4. Визначено шлях для існуючих налаштувань та estimation drafts: імпорт/міграція або явно
   описаний безпечний перенос. Старий JSON не можна мовчки оголошувати сумісним із
   .pvrelease.
5. Дозволені Jira edits мають review конкретного вмісту й окрему перевірку результату.
   Демонстрація без Jira не є live acceptance.

### Ціль 2 — функціональна дошка естимації

1. Користувач створює реальний scope через список ключів/потрібний клієнтський файл,
   бачить завантажені та недоступні задачі, може додати/видалити scope без дублювання.
2. Один екран показує колонки погоджених етапів, картки із
   ключем/назвою/оцінкою/відповідальним, кількості та підсумки в явно названих одиницях. Є
   пошук, відкриття details і повернення без втрати вводу.
3. На непідготовленій сторі користувач реально задає/змінює dev і QA
   estimate/decomposition, уточнення/AC та QA-матеріали. Gates і дозволені переходи видимі
   й працюють; повернення/зміна оцінки не залишають неправдиву готовність.
4. Збереження однозначне: системний Save зберігає видимий результат або до нього явно
   включає commit; navigation/restart і відмова private storage не гублять правки. Це
   перевіряється читанням реального файла й повторним відкриттям.
5. Оцінки узгоджені між карткою, details, підсумком і експортом; dev/QA/buffer не
   змішуються. Перевіряється щонайменше один непідготовлений → ready → змінений → повторно
   ready цикл без seeded готового прикладу.
6. Якщо спільна робота через Drive залишається підтвердженою вимогою, два користувачі
   проходять цей цикл через один файл із видимим конфліктом/захистом від перезапису.
   Окреме завантаження копії не є виконанням цього пункту; конкретний сервер або Apps
   Script цим критерієм не нав’язується.

Після цих двох приймань можна окремо оцінювати розширення — real Jira subtasks/додатковий
release approval/lease/privacy/агентне планування — відповідно до підтверджених вимог.
Сьогодні називати поточний результат готовим переносом чи готовою дошкою підстав немає.
